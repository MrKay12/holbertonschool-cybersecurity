===============================================================================
            NOVATECH SOLUTIONS - EMERGENCY ACCESS PROCEDURES
            Host: novatech-prod-03 (bastion)       Owner: Security Engineering
===============================================================================

PURPOSE
-------
Normal SSH access to novatech-prod-03 requires TWO factors:
  1. an SSH private key        (something you have: laptop)
  2. a TOTP code               (something you have: phone / authenticator app)
Passwords are disabled for SSH. This document explains how to restore access
when a factor is lost, WITHOUT weakening the controls for everyone else.

GROUND RULES (apply to every procedure below)
  - Never disable MFA globally. Bypasses are per user and time-limited.
  - Identity is verified out-of-band BEFORE any change (see 1.2).
  - Two people are involved: the requester's manager approves, a second
    administrator performs the change.
  - Every emergency action is recorded (section 5) and reviewed.
  - Keep your current root/SSH session open until a new login is confirmed.

Configuration files referenced below:
  /etc/pam.d/sshd
      TOTP step (pam_google_authenticator)
  /etc/ssh/sshd_config
      main SSH config
  /etc/ssh/sshd_config.d/00-identity-fortress.conf
      key + TOTP settings (read before sshd_config)
  ~user/.google_authenticator
      per-user TOTP secret + scratch codes
  /etc/security/faillock.conf
      account lockout (5 failures / 15 minutes)
Backups created by the hardening scripts:
  /etc/pam.d/sshd.backup, /etc/ssh/sshd_config.backup,
  /etc/ssh/sshd_config.backup.YYYYMMDD, /etc/pam.d/common-*.bak


===============================================================================
1. LOST PHONE / LOST TOTP DEVICE
===============================================================================

1.1 User actions (immediately)
  - Report the loss to the security team / helpdesk (ticket + phone call).
  - If you still have scratch codes, use one to log in (section 2) and then
    re-enroll yourself (step 1.4). No administrator change is needed.
  - If the LAPTOP (SSH key) was lost too, say so: the key must be revoked
    as well (step 1.5).

1.2 Identity verification (helpdesk, BEFORE any change)
  - Call the user back on the phone number in the HR directory (never on a
    number given in the request itself).
  - Confirm the request with the user's manager (written approval in the
    ticket).
  - For executives (e.g. CEO): verification by two people, one of them in
    person or on video. Urgency is never a reason to skip this step: it is
    exactly what social-engineering attacks rely on.

1.3 Revoke the lost device's secret (administrator)
    sudo mv /home/USER/.google_authenticator \
            /home/USER/.google_authenticator.revoked-$(date +%Y%m%d)
  The old secret (and its unused scratch codes) can no longer be used.
  From now on the user cannot log in over SSH until re-enrolled (or a
  temporary bypass is granted, section 3).

1.4 Re-enroll on a new device
  The user runs, in a session opened with a scratch code or a temporary
  bypass, or the administrator runs on the user's behalf while the user is
  present:
    ./17-setup_user_totp.sh --force            (as the user)
  or
    sudo -u USER google-authenticator -t -d -f -r 3 -R 30 -w 3 -e 5
  - The QR code / secret is shown ONLY to the user (in person or over an
    encrypted screen share), never sent by email or chat.
  - The user confirms a code from the new app, then stores the 5 new
    scratch codes offline (section 2.1).
  - Remove any temporary bypass (section 3.4), then delete the revoked
    secret file after the incident is closed.

1.5 If the SSH key was lost too
    sudo -u USER nano /home/USER/.ssh/authorized_keys   (delete the lost key)
    sudo -u USER ./19-test_mfa.sh                       (after re-deployment)
  The user generates a new key pair (12-generate_ssh_key.sh) on the new
  laptop and an administrator deploys the PUBLIC key (13-deploy_ssh_key.sh).


===============================================================================
2. EMERGENCY SCRATCH CODES
===============================================================================

2.1 What they are
  - 5 one-time 8-digit codes created by google-authenticator (-e 5) during
    enrollment. They are stored in ~/.google_authenticator.
  - Each code works ONCE, in place of a TOTP code. A used code is removed
    from the file automatically.
  - Storage: printed on paper in a sealed envelope or in the company
    password manager. NEVER on the same phone as the authenticator app.

2.2 How to use one
    ssh USER@novatech-prod-03
    (key is accepted)
    Verification code: <type one 8-digit scratch code>

2.3 After using a code
  - Count the codes left:
        grep -cE '^[0-9]{8}$' ~/.google_authenticator
  - If 2 or fewer remain, or the phone is lost for good, re-enroll
    (step 1.4) to get a fresh set.
  - Tell the security team: every scratch-code login is logged (section 5)
    and is checked against an open ticket.


===============================================================================
3. TEMPORARY MFA BYPASS (EMERGENCIES ONLY)
===============================================================================

Use ONLY when the user has no TOTP device AND no scratch code AND access is
business-critical before re-enrollment can happen (e.g. CEO travelling).

3.1 Conditions
  - Identity verified (1.2) and manager approval in the ticket.
  - Scope: ONE named user. Duration: maximum 24 hours.
  - The SSH KEY is still required. Only the TOTP step is skipped. There is
    never a password-only or key-less bypass.

3.2 Grant the bypass (administrator)
  A Match block must be at the END of sshd_config (everything after "Match"
  belongs to it):
    sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.pre-bypass
    sudo tee -a /etc/ssh/sshd_config <<'EOF'
    # EMERGENCY-BYPASS USER ticket=INC-XXXX expires=YYYY-MM-DD HH:MM
    Match User USER
        AuthenticationMethods publickey
    EOF
    sudo sshd -t && sudo systemctl reload ssh

3.3 Schedule the automatic removal (do this at the same time)
    echo 'cp /etc/ssh/sshd_config.pre-bypass /etc/ssh/sshd_config &&
          systemctl reload ssh' | sudo at now + 24 hours
  (If "at" is not installed, set a calendar reminder for two people.)

3.4 Remove the bypass (as soon as the user is re-enrolled)
    sudo cp /etc/ssh/sshd_config.pre-bypass /etc/ssh/sshd_config
    sudo sshd -t && sudo systemctl reload ssh
    sudo atrm <job number>                 (see: sudo atq)
    sudo -u USER ./19-test_mfa.sh          (must report PASSED)

3.5 Lockouts caused by failed attempts
  Not an MFA problem: unlock instead of bypassing.
    sudo ./9-faillock_manage.sh reset USER          (account lockout)
    sudo ./11-fail2ban_manage.sh unban <IP>         (IP ban)


===============================================================================
4. ROOT ACCESS RECOVERY
===============================================================================

The root password is locked (5x02) and root cannot log in over SSH. Root
access goes through sudo from an administrator account. If no administrator
can log in, use one of these paths, in this order:

4.1 Another administrator
  Any other member of the sudo group logs in (key + TOTP) and repairs the
  configuration or applies section 1 / 3 for the locked-out admin.

4.2 Hypervisor console (no network authentication involved)
  Multipass (lab):   multipass shell novatech-prod-03
  Cloud / VMware:    provider's serial or web console
  This path does not go through sshd, so a broken SSH/PAM configuration
  cannot block it.

4.3 Restore a broken SSH / PAM configuration (from 4.1 or 4.2)
    cp /etc/pam.d/sshd.backup          /etc/pam.d/sshd
    cp /etc/ssh/sshd_config.backup     /etc/ssh/sshd_config
    cp /etc/ssh/sshd_config.d/00-identity-fortress.conf.backup \
       /etc/ssh/sshd_config.d/00-identity-fortress.conf
    sshd -t && systemctl reload ssh
  Broken account lockout / password stack:
    cp /etc/pam.d/common-auth.bak     /etc/pam.d/common-auth
    cp /etc/pam.d/common-account.bak  /etc/pam.d/common-account
    cp /etc/pam.d/common-password.bak /etc/pam.d/common-password

4.4 Single-user / recovery mode (last resort, physical or console access)
  - Reboot, hold SHIFT (BIOS) or ESC (UEFI) for the GRUB menu.
  - Select "Advanced options" -> "(recovery mode)" -> "root".
    If root's password is locked and recovery asks for it: edit the GRUB
    entry (key "e"), append  init=/bin/bash  to the "linux" line, Ctrl-X.
  - Remount read-write:   mount -o remount,rw /
  - Apply 4.3, then:      sync; reboot -f
  - Afterwards: verify the GRUB menu is password-protected and the disk is
    encrypted, since this path works for anyone with console access.

4.5 Break-glass account (optional, recommended for production)
  A dedicated admin account whose key and TOTP secret are stored in a
  sealed envelope in the safe (two-person access). Every use is an
  incident; its key and secret are rotated afterwards.


===============================================================================
5. AUDIT TRAIL REQUIREMENTS FOR EMERGENCY ACCESS
===============================================================================

5.1 Before: a ticket must exist, containing
  - who requested, who approved (manager), who performed the change
  - how identity was verified (callback number, video call, ...)
  - reason, procedure used (1, 2, 3 or 4), start time and planned end time

5.2 During: record every action
  - Administrators work through sudo only (each command is logged with the
    admin's name). No shared accounts, no "sudo su -" for this work.
  - Append a line to the emergency log for each step:
        echo "$(date -Is) $SUDO_USER ticket=INC-XXXX action=<what>" \
            | sudo tee -a /var/log/emergency-access.log
  - Keep a copy of every changed file (the .backup / .pre-bypass files).

5.3 Logs to keep (minimum 1 year, read-only for non-admins)
  - /var/log/auth.log or: journalctl -u ssh _COMM=sudo
        SSH logins (method used, source IP), sudo commands
  - /var/log/emergency-access.log
  - fail2ban log (/var/log/fail2ban.log), faillock records
  Useful queries:
        journalctl -u ssh --since "24 hours ago" | grep -E 'Accepted|Failed'
        grep -i 'google_authenticator' /var/log/auth.log
        sudo journalctl _COMM=sudo --since today

5.4 After: close-out within 24 hours
  - Confirm the bypass is removed (no "EMERGENCY-BYPASS" in sshd_config):
        sudo grep -n EMERGENCY-BYPASS /etc/ssh/sshd_config
  - Run ./1-pam_audit.sh and ./19-test_mfa.sh: both must report the
    hardened state.
  - Rotate what may be compromised: TOTP secret, SSH key, break-glass
    credentials if used.
  - Security team reviews the ticket and the logs, and records the review
    (reviewer, date, findings) in the ticket.
  - Repeated emergencies for the same user or cause are reported to the
    CISO as a process issue.

===============================================================================
Review this procedure every 6 months and after every real emergency.
Test it (sections 2, 3 and 4.2) on a non-production VM once per quarter.
